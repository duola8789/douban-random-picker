# 推广文案

两处已选定渠道的现成文案。提交前请先完成 `README.md` 里的真机验收——文案里描述的行为要和你实际跑出来的一致。

## 一、阮一峰周刊投稿

**提交方式**：在 <https://github.com/ruanyf/weekly/issues> 新建 issue。
仓库没有 issue 模板，但近期投稿的标题惯例是 `【开源自荐】名称：一句话`。

**标题**

```
【开源自荐】豆瓣随机一部：从你标记的「想看」里随机抽一个的 Chrome 扩展
```

**正文**

```markdown
项目地址：https://github.com/duola8789/douban-random-picker

## 它解决什么问题

在豆瓣标记了几百个「想看」「想读」之后，选择本身变成了负担：列表越长，越难决定下一部看什么，最后往往一个都不点。

这个扩展把决定权交给骰子。点一下工具栏图标，侧边栏打开，从你自己标记的条目里随机抽一个，抽到就去看。

## 怎么用

候选来自你本人的豆瓣收藏：标记为想看的电影和剧集、标记为想读的图书。
电影 / 剧集 / 图书三个开关自由组合，也可以只抽其中一类。
抽中后显示封面、年份、豆瓣评分、你自己的评分和短评，一键跳到豆瓣条目页。
抽过的会记住，最近的不会重复抽到。

## 几个工程上的点

写在 README 里可能更有意义，这里简单提两句：

- 豆瓣的收藏接口要求请求带 Referer，而扩展里的 fetch 不能设置这个 header；
  同时 service worker 对 douban.com 属跨站，`SameSite=Lax` 的会话 cookie 不保证携带。
  所以请求放在 `*.douban.com` 的 content script 里发，同站、Referer 天然合规，
  也不需要申请 `cookies` 权限。

- MV3 的 service worker 空闲约 30 秒就休眠，分页循环放进去等于和生命周期赛跑。
  所以循环跑在 content script 里，service worker 只负责开标签页、下指令、收结果。

- 「随机」不是简单地从合并池里抽。条目数悬殊时（图书往往远多于电影），
  均匀抽取会让图书占掉大半。这里先等概率抽类别，再在类内均匀抽。

## 安装与许可证

尚未上架 Chrome Web Store，目前用开发者模式加载（README 有步骤）。
MIT 许可证，源码在仓库里。

非官方工具，与豆瓣无关联。
```

**提交前的两个硬前提**

1. 仓库里要有截图或 GIF。没有图的自荐，点开率会掉一大截。
2. 最好等 Chrome Web Store 上架后再投——「加载已解压的扩展程序」对非技术读者是一道墙。

## 二、小红书

小红书发不了图文（需要登录态和图片），下面是可以直接复制的文案。

**标题（20 字内）**

```
选择困难症的救星：随机决定今晚看什么
```

**正文**

```
我的豆瓣「想看」列表攒到四百多条了。

每次打开都是一样的界面，滚两屏，关掉，最后去看老片子。
不是没得选，是太多了反而选不动。

后来给自己写了个小工具：打开侧边栏，点一下，从我想看里随机抽一部。
抽到什么就看什么，不许反悔。

┌ 它会做什么
· 从你自己标记的「想看 / 想读」里抽，不是全网推荐
· 电影、剧集、图书可以分开抽，也可以混着来
· 抽中直接显示豆瓣评分 + 你当年写的短评
· 抽过的最近不会重复出现

└ 它不会做什么
· 不上传任何数据，没有服务器
· 不动你的豆瓣账号，不打分不写短评

最爽的是「只抽书」那个模式。通勤路上点一下，抽到哪本读哪本。

⚠️ 目前还没上架商店，要在浏览器里开发者模式加载，
   有点门槛，需要的话我另开一篇讲怎么装。

#选择困难症 #豆瓣 #书单 #电影推荐 #效率工具 #浏览器插件 #读书
```

**配图建议**

- 图 1：侧边栏抽中卡片的整体截图（要能看到「再抽一个」按钮）
- 图 2：三个类别开关，其中只勾选「图书」的状态
- 图 3：历史列表，能看出「抽过的不会重复」
- 图 4：封面做成大字标题「今天看什么，交给骰子」

小红书对「三步安装」类教程的收藏率很高，等上架商店后可以再做一篇。
