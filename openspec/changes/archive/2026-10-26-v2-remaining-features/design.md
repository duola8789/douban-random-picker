## Context

v1 的缓存维度只有 `movie:mark` 与 `book:mark`，`buildPools()` 遍历全部缓存分桶，所以「池子合并」本身几乎不需要改——只要多出 `movie:done`、`book:done` 两个维度，`buildPools()` 会自动把它们归进同一类别。

抽取的排除逻辑目前有两处：`remainingFor()` 扣去重窗口、`pick()` 扣本地已标记完成的条目（V2-4 引入）。屏蔽条目是第三类排除，适合并进同一个 `pick()`。

`content.js` 的 `fetchAll()` 已经接受 `status` 参数，是 `sync.js` 把它写死成了 `'mark'`。扩展维度只需要改调用方。

候选池页可以照搬记录页的形态：独立扩展页面、`chrome.runtime.getURL()` 打开、复用 `sidepanel.css` 的基础样式。

## Goals / Non-Goals

**Goals:**

- 让「看过的」进入候选池，且卡片能一眼看出这是重温。
- 提供唯一能管教池子的入口：看见全部候选、筛掉、屏蔽、恢复。
- 历史能筛能导出。

**Non-Goals:**

- 片单 / 书单 / 官方榜单 / 公开列表来源（接口已调研，见 ROADMAP）。
- 屏蔽数据的跨设备同步。
- 候选池页的虚拟滚动（当前的百级数据量用不上）。

## Decisions

### 1. 同步维度直接扩到四个，不做懒加载

`DIMENSIONS` 增加 `movie:done`、`book:done`，`sync.js` 下发 `status: dimension.status`，并发上限仍为 2。

**为什么**：抽取需要全量候选，懒加载会让「抽」这个动作依赖网络。用一次更长的同步换后续全程离线，符合 v1 的设计。

**代价**：首次同步与手动同步的耗时、请求量翻倍。以 1200ms 分页间隔计算，几千条收藏的完整同步从约半分钟变成一分钟左右。这是可接受的，且最短更新频率仍然兜底。

### 2. 屏蔽集合独立存储，排除逻辑放进 `pick()`

`chrome.storage.local` 新增 `hidden: { [key]: removedAt }`。`pick()` 增加 `hidden` 参数，在去重窗口过滤之后、以及 done 排除之后再做一次过滤。

**为什么**：与 V2-4 的 done 排除走同一条链路，纯函数好测；`hidden` 与 `records` 保持两套数据，删除记录不会误删屏蔽，反之亦然。

**替代方案**：把 hidden 塞进 `caches` 条目里加一个 `hidden` 字段。放弃——同步会整份覆盖缓存，屏蔽就丢了。

### 3. 候选池页走独立消息，不复用 `GET_STATE`

新增 `UI.GET_CANDIDATES`，返回 `{ items: { movie, tv, book }, hidden, pendingKeys }`。

**为什么**：`GET_STATE` 每次侧边栏打开都会调，返回全部条目会让这条高频链路多背几百 KB。候选池页是低频、按需打开的页面。

### 4. 屏蔽操作批量接口，服务端过滤待看

`UI.HIDE_CANDIDATES` 接收 key 数组，服务端读 `records`，跳过处于 `pending` 的 key，返回实际屏蔽的与跳过的。

**为什么**：批量删除的确认框在客户端已经说明数量，但「待看不可屏蔽」的最终裁决必须在写存储的一侧，否则并发窗口里仍可能屏蔽掉正在待看的条目。

### 5. 屏蔽清理挂在同步完成之后

`runSync()` 成功后调用 `cleanHidden()`：删除 `removedAt` 超过 90 天、且 key 不在任何 `caches` 条目里的屏蔽记录。

**为什么**：只有同步完成后才能可靠判断「条目是否还在豆瓣的收藏里」。放在别处会误删暂时没同步的条目。

### 6. 「重温」只出现在待看卡片上

`sourceTag()` 的 `done` 分支保持「看过 / 读过」，用于记录页的「来自『看过』」；待看卡片的 eyebrow 单独判断 `markStatus === 'done'` 显示「重温」。

**为什么**：记录页的语义是「这条属于哪个豆瓣标记」，卡片上的语义是「这次是重温」。同一个词放两处都会有一处读着别扭。

### 7. 历史筛选在前端做，导出用 Blob

记录页一次最多拿 200 条，筛选直接在前端过滤，不改消息。导出用 `Blob` + `URL.createObjectURL` + `a[download]`，文件名 `douban-random-records-2026-10-24.json`。

**为什么**：不值得为 200 条记录加服务端筛选；导出数据本来就已经在页面里。

### 8. 竖排封面居中，不改变断点

`@media (max-width: 430px)` 里给 `.card-cover` 加 `margin-inline: auto`（或 `.card-head` 居中）；再加一档 `@media (max-width: 300px)` 把封面缩到 108×162。

**为什么**：断点本身是按信息区最小宽度算出来的，动它会让信息行在边界处挤坏；只调封面位置最安全。

### 9. 归档顺序：v2-4 先

本 change 不修改 V2-4 动过的 `random-pick`「每类只有一个待看」与 `draw-history`「记录状态流转」，所以两个 change 的 delta 不重叠。但为了主 spec 的可读性，**先 archive `v2-4-mark-done`，再 archive 本 change**。

## Risks / Trade-offs

- **同步耗时翻倍** → 最短更新频率维持 10 分钟不变；首次使用只拉一次全量。若日后成为问题，再考虑把 done 维度的 TTL 调长。
- **hidden 与记录被用户混淆** → 帮助内容里明确「屏蔽 = 不再抽它，记录 = 抽过什么」；候选池页的「已屏蔽」视图提供唯一的恢复入口。
- **hidden 无限增长** → 90 天 + 条目已消失的双条件清理；仍在收藏里的屏蔽条目保留，用户随时可恢复。
- **候选池页一次渲染几百行** → 暂不虚拟滚动；用文档片段一次性插入，配合 `content-visibility: auto` 兜底。
- **「屏蔽全部筛选结果」误伤** → 二次确认里显示准确数量，并明示待看条目会被跳过。
