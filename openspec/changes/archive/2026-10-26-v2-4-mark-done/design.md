## Context

v1 的状态机已经留好了位置：`history.js` 的 `resolveRecord()` 支持写入 `done`，`makeRecord()` 也接受 `state` 参数，只是没有入口调用它们。跳过路径（`handleSkip` → `resolveRecord` → 写回 storage）可以直接复用。

候选池的构建在 `picker.js`：`buildPools()` 把缓存按类别分桶，`pick()` 接收 `history` 并扣除去重窗口。本 change 需要在同一个环节加入「已标记完成」的排除。

界面侧，待看状态下底部是 `#pending-actions` 里的两个按钮（`index.html:36-39`），由 `renderActions()` 控制文案与可用状态。

完整记录页（`src/history/`）是独立标签页，目前只渲染列表，没有任何操作。

## Goals / Non-Goals

**Goals:**

- 让「看完了」成为与「跳过」并列但语义不同的出口，且不消耗额度。
- 让本地「看过」的条目真正退出候选池，而不只是压在去重窗口里。
- 不新增豆瓣请求，不写入豆瓣。

**Non-Goals:**

- 「重温」标签与「看过的条目进池子」——属于 V2-1。
- 候选名单页与本地隐藏——属于 V2-2。
- 把「看完了」同步到豆瓣。

## Decisions

### 1. 用 `records` 的 `state === 'done'` 作为排除依据，不新增存储字段

候选池排除已标记完成的条目时，直接从 `records` 里取 `state === 'done'` 的 key。

**为什么**：删除记录即撤销排除，语义自洽；若另存一份 `localDone` 集合，删除记录后还得同步清理，反而多一份要保持一致的数据。

**替代方案**：`localDone: { [key]: markedAt }` 独立集合。放弃，因为它在「删除记录」这个动作上会分裂成两份真相。

### 2. 排除逻辑放在 `pick()` 内部，不放进 `buildPools()`

`pick()` 已经接收完整 `history`，在里面先算出 `doneKeys`，再过滤 `remainingFor()` 的结果。

**为什么**：`buildPools()` 只该关心缓存结构，不该知道记录状态；把两类数据都塞给 `pick()` 可以保持它是纯函数，便于 `node --test` 直接覆盖。

**代价**：当被排除的条目全部来自 done 时，`pick()` 仍返回 `POOL_EXHAUSTED`，界面无法区分「去重窗口耗尽」和「全部标记完成」。本版接受这个粗粒度，提示文案统一为「没有新的可抽条目」并给出清空记录的入口。

### 3. 标记完成后不自动续抽，轻提示放在空槽视图

「看完了」成功后只写记录、清掉待看状态，界面回到 `placeholderView()`。跳过则维持现有的自动续抽。

**为什么**：跳过是「现在就要换」，看完了是「这段时间结束了」。不自动续抽同时也让这条路径需要一次主动点击，不至于把跳过额度架空。

轻提示不放进现有 `#toast`，因为 toast 只渲染纯文本，加链接要么改造成支持 HTML（引入注入面），要么再写一套渲染。空槽视图本来就要出现，在「开始吧」下方加一行带链接的提示成本最低。

**状态**：`state.hint` 保存待显示的提示，`render()` 时渲染；下一次抽取或切换类别时清空。

### 4. 轻提示的显示条件用 `markStatus`

只有当条目的 `markStatus` 不是 `done` 时才提示去豆瓣标记。V2-1 之前候选池里只有 `mark` 条目，这个条件恒成立；V2-1 之后自然生效，不需要回头改。

### 5. 窄屏文案用 CSS 媒体查询，不用 JS 监听 resize

按钮内放两个 `span`：`.wide-label` 与 `.narrow-label`，用 `@media (max-width: 359px)` 切换显示。跳过次数的角标同样由 CSS 控制显隐。

**为什么**：用 JS 的 `matchMedia` 监听再触发 `render()` 会把布局变化和整棵视图的重建绑在一起，拖动侧边栏时容易抖动。CSS 切换只影响文字，不触碰渲染流程。

**代价**：DOM 里同时存在两套文案，读屏会读到隐藏的那份——用 `aria-hidden` 处理。

### 6. 删除走新的消息类型，二次确认在记录页内完成

新增 `UI.DELETE_RECORD`，`handleDeleteRecord(key)` 校验目标记录不是 `pending` 后从数组移除并写回。

记录页的确认交互不引入原生 `confirm()`（和整体气质不符），在行内把删除按钮切换成「确定删除 / 取消」两个小按钮，或者复用侧边栏的确认弹层样式。

**为什么**：确认弹层会遮住列表，而行内确认能保留上下文，也少写一个组件。

### 7. 版本号升 minor

新增「看完了」是一个能独立说出的能力，按版本策略走 minor。

## Risks / Trade-offs

- **本地「看过」与豆瓣「看过」不一致** → 帮助内容里明确写清「标记完成只写本地」。轻提示提供的去豆瓣入口是缓解手段，不是自动同步。
- **清空历史后，已完成条目回到候选池** → 可接受。清空是显式动作，且用户本来就可能想重新抽到这些条目。spec 里已把它写成「删除记录即回到候选池」。
- **记录上限 500 条裁剪掉旧的 done 记录** → 老条目可能重新出现。实际使用中 500 条足够覆盖，暂不额外处理。
- **窄屏三个按钮仍然紧** → 两字文案 + 内边距收到 10px 后，240px 下内容宽约 46px，刚好两个汉字；跳过次数用角标不占内容宽。需要在 240px 宽度下截图验收。
- **待看记录不可删的限制可能让用户困惑** → 删除入口对于 `pending` 记录直接不显示，而不是显示后报错，减少一次无效操作。

## Open Questions

- 抽到「看过的」条目时，「看完了」按钮是换成「重温完了」还是隐藏——等 V2-1 引入 done 条目后再定，不影响本 change 的任务拆分。
