## Context

候选池此前由一个全局「抽取范围」设置定义：它同时决定同步哪些维度、抽哪些来源，又和候选池页的查看筛选混在一起。用户在同一页看到两组「来源」控件、两种提交方式（范围立刻生效、条目要保存），很难分清哪个在改行为。

本次把候选池收成「勾选的集合」，来源改为按需加载。行为契约见 proposal.md 与 `specs/` 下三个 delta。

## Goals / Non-Goals

**Goals:**

- 候选池 = 用户勾选的那批条目；保存后生效，只有一种提交模型。
- 来源只在需要时联网加载一次，加载回来的条目直接进入候选池。
- 打开界面不自动同步；同步只刷新已经加载过的来源。
- 筛选（来源 / 时间 / 评论 / 池中池外）都是查看条件，不产生网络请求。

**Non-Goals:**

- 不做自动定时同步。
- 不做「加载但默认不进池」：加载即入池，避免引入第二套收录名单。
- 不新增豆瓣来源类型（豆列、榜单等）。

## Decisions

### 决策 1：候选池是勾选集合，hidden 仍是存储形式

池子的默认值是「在池里」；取消勾选并保存写入本地 `hidden` 集合，重新勾选则移除。抽取、计数、空态都按这个集合算。

- 保留 hidden 作为存储的排除名单，而不是改写成收录名单：存量数据结构不变，默认在池的语义也符合「加载即入池」。
- 代价是「加载进来的条目默认在池里」；这是本次明确的产品选择，加载弹窗会写清楚。

### 决策 2：已加载来源由缓存推导，不新增设置

某个来源只要有一个维度的 `syncedAt > 0`，就算已加载。未加载的来源不发起同步，也不出现在来源筛选的可选项之外。

- 不保留 `poolScope` 设置：它正是这次要移除的双重语义。
- 读取设置时顺手删掉 `poolScope` / `scopePromptDismissed`，避免旧值继续影响行为。
- 生产用户升级后，缓存里有哪个来源就算加载过哪个，行为与升级前一致。

### 决策 3：来源按需加载，加载即入池

来源筛选里勾上一个未加载的来源时：

1. 弹窗说明「这一半还没有加载，要从豆瓣拉取一次，加载后这些条目会进入候选池」；
2. 用户确认后才发起同步，期间展示「正在加载 …」；
3. 成功后来源加入筛选、条目按默认在池渲染；
4. 取消则勾选还原，不发请求；
5. 失败则勾选还原，并给出原因与重试提示，不假装加载过。

不采用「加载但默认不进池」：那需要把存储从排除名单改成收录名单，迁移成本大，而且「我只是看看」这个诉求可以由池中/池外筛选满足。

### 决策 4：同步目标只覆盖已加载来源

`doSync` 的目标维度：

- 显式加载某个来源时，只有该来源的两个维度；
- 手动同步时，所有已加载来源的维度；
- 本地一个来源都没加载时（异常状态）退回四个维度，保证按钮仍可用。

打开界面不自动同步。加载新来源走非 force 目标，冷却只作用于本次要拉的维度，不会被已经同步过的来源拦住。同一时间只允许一个同步在跑；加载请求遇到进行中的同步会先等它结束。

### 决策 5：同步只表达「正在同步」，不表达进度

- 同步期间主界面展示「正在同步」和一条不确定进度线；按钮变为「同步中」并禁用。
- 不展示条数、百分比或维度进度。
- 空闲时在同步按钮旁常驻展示上次同步日期；没有同步过写「还没同步过」，完整时间放在 `title` 里。
- 手动与首次同步完成后提示「更新完成」。
- 冷却期内按钮保持可点，点击时说明还需等待多久。

### 决策 6：统一筛选条，状态按已保存的池子

候选池页只有一套筛选：来源、标记时间、有我的评论、状态（全部 / 候选池中 / 候选池外）。

- 来源决定「看哪些来源」；加载是勾选来源时的显式动作，不产生第二套设置。
- 时间、评论、状态都是纯查看，不改池子。
- 状态筛选按**已保存**的 hidden 集合算：未保存的取消勾选不会让行从眼前消失，保存后才移动。
- 全选 / 反选作用于当前筛选结果，跳过待看条目；点保存统一提交移出与放回。
- 独立「不在池里」视图取消，由「状态 = 候选池外」取代；已消失的移出记录也在这个视图里展示。

### 决策 7：清理与失效判定只认本次同步覆盖的完整结果

清理移出记录依赖「条目是否仍出现在同步结果里」。只有本次同步实际覆盖的维度全部完整成功时，才允许清理与判定「已从豆瓣消失」；否则跳过，避免把这次没拉到的条目误判为已消失。

未加载的来源没有本地记录，不参与判断。

### 决策 8：候选池构建合并所有已加载缓存

`buildPools` 不再按来源过滤，合并所有已加载维度的条目，并按 key 去重（看过优先）。缓存里本来就只有加载过的维度，未加载的维度是空的。

### 决策 9：部分成功不覆盖完整缓存，也不算新鲜

部分结果不丢弃上一份完整同步的条目；标记为 partial / error 的维度不算新鲜，下一次检查重试。

### 决策 10：首次使用只加载一半

首次打开的弹窗让用户挑「想看 / 想读」或「看过 / 读过」，默认前者。选中的来源只加载一次，条目直接进入候选池；另一半以后在候选池页按需加载。取消则保持空状态，下次打开或点同步时再次提供选择。

手动同步不再询问「同步哪些」：已加载来源是唯一依据。

### 决策 11：计数、空态与「池外」都要与候选集对得上

- 侧边栏的类别计数、骨架屏判定与占位文案只统计未移出的条目；范围外的概念不再存在。
- 候选池页的页签计数是池子大小，不受查看条件影响；列表上方的计数是当前筛选结果。
- 空状态尽量指出原因：状态筛到池外、旧数据缺日期、匹配项在其它类别、或匹配项在另一个已加载但未勾选的来源。
- 已消失的移出记录只在「状态 = 候选池外」里出现，且只有完整同步证据下才给「清除」。

### 决策 12：更换账号清空旧账号数据

扩展没有独立账号，存的 uid 只是请求地址的一部分；登录态始终来自浏览器里的豆瓣会话。

更换账号由用户在豆瓣网页完成，扩展只负责：确认后清空旧账号留下的缓存、移出集合与抽取历史，清除 uid，再重新探测。这样两个账号的数据不会挤在同一份本地存储里。

同步进行中拒绝更换，避免清空与缓存写入互相覆盖。粘贴个人主页只用于确定 uid，不是登录手段，界面文案要说清楚。

## Risks / Trade-offs

- **[加载即入池，用户只想看看]** → 加载弹窗明确写出这一点；不想留的条目取消勾选并保存即可。若未来需要「只看看」，再考虑收录名单模型。
- **[来源筛选是查看条件，池子可能跨来源]** → 页签计数与「池里 N」始终按勾选算；帮助里写清「来源只影响查看，候选集由每行勾选决定」。
- **[请求量]** → 按需加载只在第一次勾选时发生；未加载的来源永远不拉。
- **[首次加载取消后界面很空]** → 空状态文案指向同步按钮；点击同步会重新提供加载选择。
- **[加载失败]** → 勾选还原，说明原因；不写入半份「已加载」状态。
- **[清理跳过]** → 本次同步不完整时不清理，孤儿记录会积累；它们无害，条件满足时清掉。
- **[同步中途关闭侧边栏]** → `GET_STATE` 的 `syncing` 恢复状态。

## Migration Plan

1. 读取设置时删除 `poolScope` / `scopePromptDismissed`，不再使用。
2. 已加载来源由现有缓存推导：有缓存的来源继续参与池子，行为与升级前一致。
3. 未加载的来源不发起请求，直到用户按需勾选。
4. 回滚：恢复范围设置需要重新引入 `poolScope`，缓存结构未变。

## Open Questions

- 四个筛选统一为下拉，放在同一行；如果之后来源选项变多，再考虑分段控件。
- 首次加载弹窗是否需要「不再提示」：当前只在首次使用出现，暂无必要。
